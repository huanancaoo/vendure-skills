# Plugin Architecture

## Use This Reference For

- Creating a new backend capability
- Restructuring feature code into a plugin
- Registering entities, providers, GraphQL extensions, or events

## Core Rule

Default to a plugin when the feature is not a one-line bootstrap setting. A plugin is the unit that keeps entities, services, API extensions, and configuration aligned.

## Recommended Shape

```ts
@VendurePlugin({
  imports: [PluginCommonModule],
  providers: [FeatureService],
  entities: [FeatureEntity],
  adminApiExtensions: {
    schema: adminApiExtensions,
    resolvers: [FeatureAdminResolver],
  },
})
export class FeaturePlugin {}
```

## CLI-Aligned Layout

Prefer the structure generated by `npx vendure add` when starting from a new plugin. The current official examples place plugin files under `src/plugins/<plugin-name>/` with these common children:

- `api/` for GraphQL schema extensions and resolvers.
- `entities/` for plugin-owned database entities.
- `services/` for business logic and persistence access.
- `<plugin-name>.plugin.ts` for the `VendurePlugin` declaration.
- `constants.ts` for shared tokens, permissions, and stable identifiers.
- `types.ts` for plugin-local TypeScript types.

## Design Rules

- Keep the plugin class declarative. Put behavior in services.
- Use `PluginCommonModule` for shared Vendure primitives unless the plugin has a narrow reason to avoid it.
- Register `entities` only when the plugin owns a first-class data model.
- Use `configuration` when the plugin must update `VendureConfig` during bootstrap.
- Register `providers` for services, event handlers, and supporting classes.
- If the plugin also exposes Dashboard UI, stop here and switch to `vendure-dashboard` for that UI surface.

## Service Boundary

- Let resolvers validate input shape and delegate orchestration.
- Let services own transactions, persistence, and interaction with other Vendure services.
- Pass `RequestContext` from resolvers into services so channel, language, active user, and transaction context stay intact.
- Use `TransactionalConnection` with the current `RequestContext` for database access instead of raw TypeORM connection access.
- Keep naming aligned across plugin, service, entity, and API types so the feature stays discoverable.

## Event and Permission Hooks

- Use the event bus when the feature reacts to Vendure lifecycle events.
- Introduce explicit permissions when a new Admin API capability changes who may execute it.
- Keep permission naming feature-specific so policies stay readable.
